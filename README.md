# Embedded Labs

An interactive, browser-based learning platform for embedded systems programming on
Arduino, inspired by [HDLBits](https://hdlbits.01xz.net). Learners write real Arduino
C/C++ code, see it compiled with the real toolchain, and watch it run against a
simulated circuit — all in the browser, with automatic grading against expected
pin/peripheral behavior.

## Why this is feasible

Unlike most "run untrusted code" platforms, we don't execute learner code on our own
servers. Compiled machine code runs inside a CPU emulator in the *learner's browser*,
which is both safer (no sandboxing needed for execution, only for compilation) and
cheaper to scale (simulation load never touches our infrastructure).

## How it works

1. Learner writes an Arduino sketch (`.ino`) in an in-browser editor.
2. The sketch is compiled server-side against the official Arduino AVR toolchain
   (`avr-gcc` + [ArduinoCore-avr](https://github.com/arduino/ArduinoCore-avr)),
   producing a `.hex` file — the same artifact Arduino IDE would produce.
3. The `.hex` file is sent back to the browser and executed by
   [`avr8js`](https://github.com/wokwi/avr8js), an open-source, cycle-accurate AVR CPU
   emulator (MIT licensed).
4. Simulated peripherals are rendered visually using
   [`@wokwi/elements`](https://github.com/wokwi/wokwi-elements) (MIT licensed) — LEDs,
   servos, sensors, etc.
5. A per-exercise checker function inspects the pin/peripheral state timeline produced
   by the simulation and grades correctness — the same role a testbench plays in
   HDLBits.

## Repository layout

```
embedded-labs/
├── ArduinoCore-avr/        official Arduino AVR core source (submodule-like, cloned)
├── build.sh                 compiles a .ino sketch into a .hex using avr-gcc directly
├── sketches/                sample/reference sketches used for testing the simulator
│   └── 01_blink/
├── frontend/                 the in-browser simulation prototype
│   ├── src/main.js           avr8js + wokwi-elements glue code
│   ├── index.html
│   └── dist/                 bundled output (generated by esbuild)
└── docs/                     design notes and findings
```

## Status

This is an early technical proof-of-concept validating the riskiest part of the
platform: can real, compiled Arduino code run correctly inside a browser-based
emulator, fast enough for interactive use? **Yes** — confirmed working for digital
I/O and timing (`pinMode`, `digitalWrite`, `delay`, `millis`).

Not yet built: the code editor UI, the compile backend/API, exercise content, grading
checkers, user accounts, and the broader curriculum.

## Key technical findings so far

- `avr8js` requires the correct peripheral objects (e.g. `AVRTimer` for Timer0) to be
  instantiated to match what the compiled code actually uses. A sketch using `delay()`
  will silently stall in the emulator without a `Timer0` instance, since `delay()`
  depends on the millis() interrupt-driven counter. This means our simulator setup
  needs to grow to match whichever peripherals (timers, PWM, ADC, etc.) each exercise's
  sketch relies on.
- `downloads.arduino.cc` (used by `arduino-cli`'s board manager) may not be reachable
  from all network environments (including this sandbox). We compile directly against
  the [ArduinoCore-avr](https://github.com/arduino/ArduinoCore-avr) source (mirrored on
  GitHub) using `avr-gcc`, which avoids that dependency entirely and gives us full
  control over the build process — useful for a production compile service anyway.
- The `intel-hex` npm package depends on Node's `Buffer` and cannot be used in the
  browser as-is. We use a small hand-written Intel HEX parser instead
  (`frontend/src/main.js`).
